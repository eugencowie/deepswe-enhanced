# 0001: Toolchain conventions for the scaffold

**Vite config merges layered objects via `defineMergedConfig`.** The array-merge helper in `vite.config.ts` keeps template-generated defaults (`baseConfig`, `vitePlusConfig`) separate from project overrides (`projectConfig`). Three static objects don't need it yet; it earns its keep when `reactConfig` and the Tailwind config join in leaderboard-table ticket 01.

**Routine mise tasks delegate one-for-one to `vp`.** Each routine task is a thin wrapper, which doubles the edit surface when a command changes. That cost is accepted because `mise tasks` is the discovery mechanism: a contributor with only mise installed can list everything the project can do. A few tasks are exceptions. `e2e` and `deploy:dry-run` run `vp build` first, because their scripts use the existing build. `upgrade` combines mise maintenance with a hidden nested task for the Vite+ upgrade. mise resolves a task's tools when that task starts, so the nested task forces mise to load the newly upgraded Vite+ before running `vp`. Only the user-facing `upgrade` task is listed; its nested task is hidden because it is an implementation detail.

**`validate` is the one check gate, in the template's shape.** The `validate` script runs `vp build`, `vp check`, `vp test`, `vp run e2e` and `vp run deploy:dry-run` in that order, and `validate.yml` runs `vp run validate` as one `validate` job. The astro template and the portfolio follow the same pattern, so the projects validate the same way. The e2e suite serves the existing build with `vp preview` rather than building its own. Chromium comes from the `@playwright/browser-chromium` devDependency, so installing dependencies is the only setup. The suite's smoke test asserts the built table renders with no failed requests, in place of checking by hand that the deployed site loads. The Wrangler dry-run deploy fails on a broken `wrangler.jsonc` before it can reach the Worker.

**GitHub Actions deploys through Wrangler, and the merge is the gate.** `deploy.yml` builds and runs `wrangler deploy` on every push to `main`, and `preview.yml` builds and runs `wrangler preview` on every pull request, both through `cloudflare/wrangler-action`, as the portfolio does. Neither workflow runs checks: the default-branch ruleset allows a merge only with a passing `validate` check, and a preview is not production. Cloudflare Workers Builds did this before, but kept its settings in the dashboard, listed by hand in a `wrangler.jsonc` header, and needed the Node and pnpm versions copied over on every upgrade. The workflows install the way `validate.yml` does, so nothing is copied, and each workflow's header lists the secrets and variable it reads. The custom domain stays a Worker setting and the site URL is a repository variable, so no config file names the domain. The build is for the root path, where the custom domain serves the site. Deriving the base path at deploy time only ever served the GitHub Pages project URL, so it was dropped along with the sentinel-base e2e build that guarded it.

**UI components come from shadcn/ui on Base UI primitives, with Tailwind.** Chosen for familiarity and usable defaults; the one genuinely fiddly component (the per-model multi-select dropdown) gets its behaviour from Base UI rather than being hand-written. Charts were explicitly not a factor in this decision, though a chart view is a plausible post-MVP feature (the DeepSWE site offers one) and shadcn would accommodate it. Implementers should pair shadcn's table markup with their own TanStack Table wiring rather than stacking two table abstractions.
